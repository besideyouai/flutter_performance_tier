# Flutter Performance Tier PACKAGING

Date: 2026-06-11
Status: current packaging and deployment fact source
Scope: `packages/flutter_performance_tier/`

This document owns package identity, versioning, signing, artifact, and
deployment rules for `flutter_performance_tier`.

## Current Packaging Stage

This is a private Flutter plugin package inside the `harrypet_flutter` workspace.
It is not prepared for public `pub.dev` publishing and currently uses
`publish_to: 'none'` plus `resolution: workspace`.

The package is entering an Android-first performance monitoring refactor.
Breaking package APIs, MethodChannel payloads, example workflows, and report
formats is allowed when the migration is explicit and documented.

## Artifact Types

1. Source package consumed by other workspace members through a path dependency.
2. Android plugin/library artifacts generated by consuming Flutter/Android
   builds; these are not committed from this package.
3. Example app APKs or installables for manual validation; these are human-built
   artifacts and are not committed.
4. Android performance reports generated at runtime on device; these are
   diagnostic artifacts, not release artifacts.
5. Offline analysis outputs under `build/` or a caller-provided output directory;
   these are generated artifacts and are not committed unless explicitly curated
   as small redacted fixtures.

## Signing or Publishing

- No signing credentials, keystores, or key property files may be committed.
- The example release configuration currently uses debug signing and is not a
  distribution posture.
- Publishing to `pub.dev`, Maven, CocoaPods, or an internal artifact repository
  requires a separate packaging plan and updated identity/version rules.

## Versioning

During the Android monitoring refactor, the package version is not a stable
semantic-versioning promise to external consumers.

When changing public Dart APIs, MethodChannel contracts, report schemas, Android
storage paths, or example validation flows, include a clear breaking-change note
in the task summary or PR description. Update `README.md`, `SPEC.md`, `TEST.md`,
and migration notes as needed.

Report schemas must carry their own schema version once report generation becomes
a first-class feature. Do not rely only on the Dart package version to interpret
pulled reports.

## Artifact Naming

Current Android V1 skeleton report names use this shape:

```text
performance_tier_v<schemaVersion>_<utcTimestamp>_<reportId>.json
```

`DefaultPerformanceTierService` report ids include a service session id and a
per-service sequence. Android native write handling must choose a non-existing
file name if a requested name already exists, so repeated device-side writes do
not overwrite earlier reports.

The application id is carried by the app-private storage context and the
host-side `run-as <applicationId>` retrieval command rather than embedded in the
V1 file name. If reports from multiple application ids are copied into one host
folder, the host output directory or host file name must include the application
id.

## Validation

Before sharing Android monitoring artifacts as ready for consumption, collect:

1. Non-device automated test evidence for schema/model/contract changes.
2. Manual real-device report generation evidence.
3. Manual `adb` or `@test-android-apps` retrieval evidence.
4. Parse/analyzer evidence for at least one pulled report.
5. A documented migration note for every breaking API, channel, storage, or
   report-schema change.
